# Аудит перед Stage40: совместимость ИИ, проверок и ФРВ с Stage38

Дата: 23.11.2026. Проверяемая база: **Stage39, принятая в `main`**. Статус: **АУДИТ ВЫПОЛНЕН; выявлены точечные расхождения**. Изменений в исходники работающего приложения этим аудитом не вносилось.

## Правило Stage38

У шага СОП остаётся **одно** поле `steps[].reason`:
- одна общая причина **без нумерации** допустима;
- несколько разных причин в том же поле: `1. ...\n2. ...\n3. ...`;
- количество причин не обязано совпадать с количеством Key Points;
- порядковые номера не являются разрешёнными производственными числовыми параметрами;
- Excel/TWI должны сохранять переносы и номера, без добавления столбцов/листов.

## Реальная проверенность

- **PASS в CI** Stage39 ([#45112629556](https://github.com/shonentez-afk/SOP-generanjr/actions/runs/45112629556), [#45112635563](https://github.com/shonentez-afk/SOP-generanjr/actions/runs/45112635563)); исторические тесты Stage38 проверяют `stage38ReasonText`, локальные замечания, то, что `1.` и `2.` не являются «выдуманными параметрами», отклонение `25 Н` без источника, настоящий Chrome/ExcelJS/openpyxl, выравнивание/высоту, сохранность корпоративского XLSX и TWI.
- **Не покрыто прицельными тестами Stage38:** `aiFillField` для Key Point / Reason с многими причинами, автокритерий №7 чек-листа без нормативной ссылки, передача многострочной причины из независимого ФРВ, исправление причины в продвинутых предложениях Stage27 и фиксы единой ИИ-проверки.
- **Реальный промышленный ответ Yandex AI** в этом аудите не запрашивался; вывод относится к проверенному исходному коду и опубликованным автоматическим тестам, а не к качеству конкретных запросов модели в производстве.

## Рекомендуемая работа перед Stage40: точечная Stage39.1

1. **P0:** заменить автокритерий №7 «есть нормативная ссылка» на оценку наличия содержательных Reasons Why при действительно заданных Key Points; нормативы не обязательны, семантическую достоверность оставить наставнику/инженеру.
2. **P0:** после ответов ИИ по Key Point / Reason запускать общий непереписывающий валидатор: номера являются редакционными, неизвестные технические числа не принимаются, если предлагаемый текст ломает нумерацию или меняет связь KM→Reason — показать пользователю и сохранить исходное до подтверждения.
3. **P1:** передавать ИИ при доработке Key Point полный контекст шага (Action, остальные Key Points, единое поле Reasons), но разрешать менять только выбранный КМ. Дополнить промпт единой проверки явным контрактом Stage38 и валидацией `fixValue` для причины.
4. **P1:** дополнить «Анализ ФРВ»: на этапе формирования проекта СОП редактируемое многострочное поле причины, сохранение `\n` и нумерации, отсутствие принудительного отношения 1:1 между КМ и причинами. **Не менять** структуру фактических замеров и независимые архивы ФРВ. Для наблюдений ФРВ один Key Point может оставаться достаточным; стадия составления СОП должна поддерживать полный корпоративный формат.
5. **P1:** добавить браузерные интеграционные тесты полного пути: генерация из описания → доработка КМ/причин → полная проверка/чек-лист → XLSX/TWI; отдельно ФРВ → проект СОП → проверка причин. В сценариях с фиктивными числами проверять отказ без изменения документа. Обязательная Linux/Windows регрессия.

**Не трогать:** базовые принятые 67 модулей Stage39, настройки/транспорт Yandex Cloud, ISO7010, фото/IDB, корпоративный XLSX, существующую схему `steps[].reason`, измеренное время ФРВ. Исправления разрабатывать изолированно в отдельной ветке; слияние только после CI и пользовательской приёмки.

Stage40 («Было → Стало») не начинать до согласования указанной логики, иначе новый интерфейс будет показывать несовместимые по правилам Stage38 предложения.
