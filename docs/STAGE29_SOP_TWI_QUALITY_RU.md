# Stage 29 — качество генерации СОП и TWI (не интеграция ФРВ)

**Решение владельца проекта 19.11.2026:** приоритет — повысить качество автоматически созданного СОП и производного TWI; **связку ФРВ → СОП → TWI пока не разрабатывать**. ФРВ остаётся самостоятельной необязательной функцией.

**Ветка-кандидат:** `feature/stage29-sop-twi-quality-20261119`, [PR #24](https://github.com/shonentez-afk/SOP-generanjr/pull/24) — черновик, без автоматического объединения. [GitHub Actions: 79/79 unit PASS, Chrome Linux/Windows PASS](https://github.com/shonentez-afk/SOP-generanjr/actions/runs/44487301954). **Реальную YandexGPT-приёмку пользователь ещё не выполнял**. **База:** Stage28, принят на `main`. Файл для настольного Chrome/Edge `file://`: `releases/stage29-sop-twi-quality-browser-candidate.html`.

## Цель

Уменьшить объём ручных исправлений при первом создании СОП и TWI, не добавляя ещё один интерфейс, мастера или вторые запросы к ИИ. Генерация остаётся двумя привычными действиями: **«Сгенерировать СОП»** и **«Сформировать TWI»**. TWI создаётся строго **из уже составленного СОП**, без обязательной ФРВ.

## Реализовано

### Качественный СОП

- Уточнён единый промпт генерации по TWI JI: один завершённый Important Step, Key Points только если критичны (0–3), Reason Why привязан к факту, наблюдаемый критерий. Нулевая необходимость фотографии допустима.
- В запросе учитываются не только описание операции, место/инструменты/материалы, но и **уже введённые условия безопасности**.
- Проверка результата выполняется **до применения к редактору**. Отбрасываются технические placeholders `null/keep/undefined`; удаляются повторяющиеся Key Points; одинаковые Important Steps становятся конкретными вопросами инженеру.
- **Неизвестное время нельзя превращать в измерение.** Если модель вернула время, которого не было в исходных данных, оно заменяется на `null` с вопросом об уточнении. Явно указанное время (например, 40 секунд) сохраняется.
- Неподтверждённые **числа и параметры** (например, давление 500 бар, которого нет в описании) блокируют весь опасный результат до изменения существующего СОП. Причина понятна пользователю. Другие безопасные текстовые предложения проходят штатный предпросмотр/отмену.
- Первая генерация в пустом СОП остаётся одним нажатием; повторная — через уже существующий предпросмотр «Добавить / Заменить / Оставить». Никаких новых окон.

### TWI на основе реального СОП

- Уточнена инструкция к четырём этапам Job Instruction: готовность сотрудника, **показ каждого шага СОП**, критичные детали и их реальные причины, пробное выполнение по критериям, сопровождение без придуманной периодичности.
- **При первом создании** все `present.round1`, `present.round2`, `present.round3` и при наличии критериев `tryOut.check` строятся детерминированно из текущих действий, Key Points, Reason Why, success criteria СОП. Даже если модель отвечает слишком общо, раздел показа остаётся конкретным и полным.
- Если Key Points/Reasons отсутствуют, TWI не выдумывает их и прямо поясняет необходимость уточнения у инженера.
- Модель продолжает формировать человеческие пояснения для подготовки, практики и сопровождения; новые технические цифры/частоты без источника проверяются и отклоняются, необоснованные «каждую смену / еженедельно» заменяются нейтральной рекомендацией.
- **При повторной генерации** альтернативные тексты модели показываются в старом **окне сравнения с чекбоксами**: пользователь может выбрать новые формулировки, но ручные изменения защищены и исходный TWI не перезаписывается при отмене. Числа, отсутствующие в исходных данных, всё равно не принимаются.
- Инструктор и обучаемый сохраняются. История и `sourceSignature` остаются совместимыми с действующей архитектурой.

## Границы

- **Нет изменений:** облачного прокси Yandex Cloud, адреса, env-переменных, модели/маршрутизации, транспорта, генератора/анализа ФРВ, ISO 7010, локального ExcelJS, фотографий, разметки, импорта/экспорта, системы версий, оформления блока СОП/TWI.
- Новых функций в интерфейсе нет — это пакет **качества результата**, а не кнопок.
- Ни один детерминированный валидатор не гарантирует полную технологическую корректность. Инженер всё равно должен проверить инструкцию, нормативные требования, опасности и пригодность для своего оборудования.
- При слишком большом СОП валидатор откажется незаметно обрезать учебные списки TWI; лучше явно сообщить об ограничении, чем потерять шаги.
- Онлайн-приёмка настоящего Yandex Cloud обязательна у владельца; CI использует подставные ответы ИИ и выполняется без сети.

## Проверка в реальном браузере

1. Сформировать СОП по знакомой операции со временем **и без времени**: неизвестная длительность не должна появиться как факт; Key Points должны быть конкретными, а не формальными.
2. Из этого СОП создать TWI: во втором этапе должны быть видны все реальные действия по порядку, конкретные Key Points и их причины; пробная работа проверяется по критериям СОП. ФРВ заполнять не требуется.
3. Изменить формулировку TWI вручную, повторить генерацию. Убедиться, что открывается сравнение, ручной текст сохранён без явного согласия и отмена не меняет план.
4. Проверить отсутствие придуманной периодичности проверки, новых допусков/чисел, посторонних инструментов и СИЗ. При проблемах прислать формулировку и контекст описания — валидаторы не претендуют на полный семантический аудит.
5. Проверить работу уже принятых «Проверить весь СОП», «Логика шагов», библиотеки, фото, Excel, ФРВ. Они не должны измениться.
