# Аудит ИИ-функций и архитектуры Конструктора СОП — 19.11.2026

## Уточнение пользователя — правильная роль TWI в Конструкторе СОП (19.11.2026)

**Принятый пользовательский сценарий:** сначала создаётся и редактируется СОП; затем TWI **автоматически генерируется из этого СОП**; пользователь **может необязательно поправить полученный план после генерации**. Самостоятельное конструирование TWI с нуля, обязательная ручная подготовка TWI и независимый от СОП жизненный цикл **не входят в план развития**.

Проверка Stage 18: `generateTwiPlan()` собирает `operation`, `executor`, `workplace`, `safety` и шаги с `action`, `keyPoints`, `reason`, `successCriteria`, `decisionPoints` из `state` и передаёт `AI_SYS.twiGenerate` через `aiAsk`. Затем заполняет `state.twi` и интерфейс. `htmlToTwi()` принимает ручные изменения уже сформированного плана. В текущем коде повторное создание `state.twi` целиком заменяет существующий объект, что может стереть ручную доработку; это риск для будущего пакета A, а не причина превращать TWI в самостоятельный редактор.

**Корректный вариант улучшения:** привязать результат TWI к конкретной редакции СОП; при изменениях ключевых шагов/Key Points/Reasons Why сообщать, что план требует проверки; при повторной генерации показывать обновления и предлагать сохранить или согласованно заменить ручные поправки. Первая генерация из СОП должна оставаться простой, без обязательных промежуточных подтверждений для пустого TWI. Дополнительные тренировочные вопросы, если внедрять их, также **автоматически** получать из существующих данных СОП, а не требовать отдельного ввода.

**Целевая цепочка:** [необязательная ФРВ] → СОП → ИИ-план TWI → [необязательные ручные поправки]. TWI зависит от СОП, но не требует наличия ФРВ. Это **не** отдельный проект TWI Audit RC1 из ветки `project/twi-audit-20261118`.

## 2. Влияние недоделанной модульности на уже возникшие дефекты

| Дефект | Связь с архитектурой | Подтверждённая причина / доказательство |
|---|---|---|
| Stage 15 → перестала нажиматься «Разметить» | **Прямая, высокая** | При замене загрузчика пиктограмм удалена общая функция `blobToDataUrl`, хотя редактор и IndexedDB продолжали использовать её. Stage 16 восстановил её. Общий сервис медиа не был отделён контрактом |
| Stage 16 → нет фото в XLSX | **Высокая** | Живые шаги нормализовали `normalizeStepShape`, которая обнуляет `imageData/imageBuffer` для черновика. Экспорт разрушал принадлежащие редактору данные; Stage 16 ввёл `normalizeExcelStepKeepingPhoto` и `ensureStepImagesForExport` |
| Stage 16 → Excel не распознавал изображения | **Нет прямой связи** | ExcelJS создавала неподходящий `oneCellAnchor editAs`, потребовался `twoCellAnchor` и OOXML/openpyxl-проверка. Даже модульный код мог допустить эту ошибку без интеграционного теста |
| Stage 17 → `Unterminated fractional number in JSON` | **Косвенная** | `sendDispute` полагался на `JSON.parse(extractJson(await aiAsk(...)))`, формат/транспорт/представление не имели отдельного контракта. Точная первопричина неполного ответа (прокси, сеть, модель) не подтверждена |
| Stage 18 → `keep`/`null` в речи наставника | **Косвенная** | Обработчик принимал свободный текст модели вместо JSON и отображал его целиком. Бизнес-вердикт и текст UI были смешаны |
| Stage 13 → потеря фото при импорт→черновик | **Высокая связность импорта и хранилища** | Stage 14 исправил сохранение в IndexedDB перед принятием документа. Полноценная Windows/сетевая приёмка ещё открыта |

**Вывод:** монолит и текстовые патчи повысили риск побочных изменений, но не являются универсальной единственной причиной. Необходимо одновременно: (1) отделить исходники по контрактам, (2) запретить разрушительные побочные эффекты, (3) усилить реальные интеграционные тесты. Разделение на файлы само по себе не исправит XML-якоря и нестабильный формат ответа модели.

## 3. Дополнительные риски, обнаруженные при чтении Stage 18 (не путать с подтверждёнными сбоями в эксплуатации)

1. **P0: потеря пользовательской работы при повторной генерации.** `generateSOP` непосредственно присваивает `state.steps=sop.steps.map(...)` и заменяет `safetyIconIds`, без этапа сверки/подтверждения. `frvStudyBuild` задаёт `d.cycles=[...]`, `generateTwiPlan` перезаписывает `state.twi`. Это кодовый риск потери несохранённых правок/наблюдений; отдельного пользовательского воспроизведения ещё нет. Предусмотреть транзакционный preview и отмену до изменения состояния.
2. **P0/P1: не сохраняется история наставника.** `collectDraft` сериализует `deferredIssueKeys`, но **не** `reviewIssues`, `reviewSummary` и `thread`; `applyDraft` делает `reviewIssues=[]`. Между тем интерфейс для снятого замечания сообщает «История диалога сохранена». Следовательно, после восстановления черновика история не гарантируется. Исправлять с миграцией и изоляцией по документу/версии; проверить также snapshot библиотеки, экспорт и конфликтные версии.
3. **P1: несовместимые правила Key Points.** Системный промпт генерации разрешает **0–3** действительно критичных ключевых момента, а `runDeterministicChecks` всегда добавляет предупреждение «Нет ключевых моментов» при `kms.length===0`. Нужно проверять необходимость по контексту, а не принуждать к искусственному заполнению.
4. **P1: ложное замечание о фото.** `runDeterministicChecks` опирается на `!s.imageData` для «Шаг без фото», не учитывая `imageBuffer`, `hasPhoto`, ключи фото документа в IndexedDB и случаи, когда снимок действительно не обязателен. Вместо обязательной претензии — проверка наличия медиа в сервисе фото и условная рекомендация по доказательности шага.
5. **P1: разбросанные JSON-обработчики.** `extractJson` применяется для СОП, review и TWI; ФРВ использует отдельный `parseFrvAIJson`; диспут — `mentorParseDisputeResponse`; `aiAsk` вызывает `r.json()`. Для каждого задания нужны свой валидатор/адаптер, но единая базовая обработка HTTP и формата с классификацией ошибок.
6. **P1: fallback модели срабатывает на любой `!r.ok`**, если текущая модель не дефолтная. Нужно различать недоступность конкретной модели и 401/403/429/обрыв/5xx, не скрывать истинную ошибку и не удваивать лимиты/расходы. **Это проектное предложение, а не разрешение менять модели/прокси.**
7. **P1: сетевой таймаут охватывает `fetch`, но таймер снимается до `r.json()`**, то есть чтение тела/декодирование отдельным ограничением не защищено. Нужны безопасные лимиты по длительности и размеру ответа и корректное сообщение об обрыве.
8. **P1: AI-результат может устареть во время запроса.** После `await aiAsk` функции изменяют текущее состояние без сравнения снимка/версии документа и шагов с теми, что отправлялись на проверку. Требуется `documentId` + `revision/hash` + проверка неизменности перед «Применить».
9. **P1: нет явного отделения утверждённых фактов от предположений.** Промпты требуют не придумывать факты (это сильная сторона), но структура ответа не содержит машинно-проверяемых меток `explicit/inferred/unknown` и идентификаторов подтверждающих исходных полей. В review их желательно добавлять, не превращая рекомендации в «проверенный норматив».
10. **P2: длинные префиксы и технические поля ответа обрабатываются частными регулярками.** Stage 18 устранил известный `keep/null`; системно нужен `presenter`, отображающий только разрешённые поля структурированного результата, а не вычищающий внутренние поля из произвольного текста.
11. **P2: список замечаний ограничен 15** (факт `validateReviewResponse`); для длинных СОП стоит проверить разбивку по шагам и сводную дедупликацию, чтобы не терять существенные отклонения.
12. **P2: реальные снимки пока не анализируются моделью.** `generatePhotoHint` — текстовая подсказка; не приписывать ИИ визуальную проверку до появления разрешённого мультимодального канала и тестов.

### Контуры ответственности (предлагаемая структура, НЕ реализована)

| Контур/целевой модуль | За что отвечает | Чего не должен делать |
|---|---|---|
| `core/document-state`, `core/snapshot` | неизменяемые снимки СОП, revision, валидатор структуры, транзакции изменения, сопоставление версий | знать про DOM, IndexedDB, fetch/прокси |

| `ai/transport` | только отправка к **существующему** AI proxy, время/лимиты, HTTP ошибки, разрешённый fallback, статус запроса | JSON-логика конкретного задания или изменение UI |
| `ai/protocol` | `TaskSpec`, парсинг JSON, схемы полей (СОП, review, dispute, ФРВ, TWI), ошибки `format/schema/transport` | менять состояние СОП |
| `ai/tasks/*` | подготовка входных данных, запуск задачи, проверка и возврат типизированного `proposal` | напрямую обновлять `state.steps`, DOM или IndexedDB |
| `ai/evidence` | ссылка на исходный факт/наблюдение, `confirmed/derived/unconfirmed`, причины и предупреждения | выдумывать нормативы/значения |
| `ai/ui` | предпросмотр отличий, только пользовательские поля, статусы ИИ и «Система», подтверждение | показывать `keep/null`, сырую ошибку JSON или тайные поля |
| `documents/review-history` | история замечаний и диалогов по document ID / version, миграция и перенос резервных копий | хранить исключительно в переменной RAM |
| `excel/export` | читать неизменный снимок документа и проверенное медиа, генерировать валидный OOXML | пересоздавать/нормализовать живые шаги с потерей фото |
| `app/bootstrap` | сборка и связывание зависимостей | держать всю бизнес-логику внутри одного обработчика DOM |

**Не переходить на внешние JS-import/fetch для `file://`**. Модули — отдельные исходники на этапе сборки; сборщик выдаёт **один HTML**, запускаемый двойным щелчком без сервера и соседней папки. Сохранять имеющийся proxy, модели, промпты, FRV/TWI, IndexedDB/localStorage, DOC/XLSX, версии, архив и desktop-only scope. Изменение схемы сохранения — только версионированная миграция и тесты на старых документах.

### Минимальный контракт ИИ (идея, не существующий API)

- `AIRequest { task, documentId, documentVersion, inputRevision, inputSnapshot, outputContractId }`
- `AIResult { status: ok|network_error|http_error|format_error|schema_error|stale, data, warnings, requestId }`
- `proposal` содержит изменения для сравнительного экрана и provenance, но **не** производит commit автоматически.
- `acceptProposal` делает проверку `inputRevision`, запрета редактирования опубликованных документов и наличия подтверждения пользователя, затем применяет атомарно либо возвращает конфликт.
- На экране показывать «обнаружено алгоритмом», «предложено ИИ», «подтверждено человеком», «нужен источник», а не смешивать их в одну оценку.

## 6. Технические рекомендации и внешняя проверка

- По официальной документации Yandex Cloud возможность `structured output`/JSON Schema заявлялась для YandexGPT 5 Pro (https://yandex.cloud/ru/blog/posts/2025/02/yandex-gpt-5-0). Это **не означает**, что конкретная установленная Cloud Function принимает новый параметр, либо что все текущие модели и формат прокси его поддерживают. Сначала проверить контракт текущего прокси на безопасных тестовых данных; **не менять его и настройки без запроса пользователя**.
- Документация Yandex Cloud рекомендует отдельный шаг форматирования/очистки ответов при нестабильной выдаче JSON (https://yandex.cloud/ru/docs/foundation-models/gpt-prompting-guide/popular-problems-solving). Это запасной вариант после валидатора, а не разрешение автоматически преобразовать необоснованное объяснение в юридический факт.
- Не хранить секреты, содержимое производственных СОП, реальные персональные данные, фото и полные промпты с чувствительным контекстом в Git или обычном телеметрическом логе. Для диагностики достаточно типа ошибки, task, времени, модели/версии, технического requestId и усечённого обезличенного фрагмента при разрешении пользователя.
