# Уточнённый аудит ФРВ и «Анализа ФРВ» — Stage32.2

Дата: 20.11.2026. **Редакция 2, с учётом уточнения пользователя.** Это проектное решение/аудит, а не реализация; принятая Stage32.2 и действующие JS-модули не менялись.

## 0. Обязательное назначение двух разделов

Пользователь уточнил исходную задачу: **«Анализ ФРВ» — самостоятельная отправная точка для наблюдения, измерения, поиска потерь, оптимизации работы и последующего ПЕРЕНОСА подтверждённых результатов в новый проект СОП**.

Мой прежний вывод «убрать передачу из ФРВ в СОП» был неверен. Снимается предложение ликвидировать СОК-кандидата и кнопку создания СОП как функции; следует **упростить их UX и сделать перенос безопасным**.

Два направления работы не являются лишним дублированием по назначению:
- **Редактор СОП → «ФРВ»**: если СОП уже есть, ФРВ служит его рабочим листом/хронометражем в XLSX, данные берутся из шагов СОП.
- **«Анализ ФРВ» → проект СОП**: ФРВ может **создаваться с нуля**, без готового СОП и без описания в редакторе СОП. От наблюдений и замеров — к анализу и пересмотру процесса — к проекту СОП, который человек дорабатывает и утверждает.

Это **не обязательная сквозная цепочка ФРВ→СОП→TWI**. TWI, как прежде, генерируется только из СОП и отдельно по выбору пользователя. Начать с анализа ФРВ можно, но не обязательно.

## 1. Что есть в текущем коде

| Сценарий | Источник данных | Что получает пользователь |
|---|---|---|
| «ФРВ» (после редактора) | \`state.steps[].durationSeconds\` + \`state.steps[].frv\` | Лист «ФРВ» в XLSX; расчёт ВДЦ/М1/М2, перемещений, целей |
| «Анализ ФРВ» (независимые наблюдения) | \`state.frvStudy.cycles[].observations[]\` | Отдельные реальные замеры, анализ ценности/потерь, предложения ИИ, кандидаты для стандарта |
| Перенос | \`frvStudyMakeSok()\` затем \`frvStudySendSop()\` | Создаёт шаги СОП в редакторе (сейчас небезопасно — см. ниже) |

- Вкладка «Анализ ФРВ» содержит **19 колонок на наблюдение**, 8 полей паспорта, несколько стадий статуса и отдельные подтверждения ИИ. Важно не отменять экспертные возможности, а убрать их из основного сценария.
- \`frvStudyBuild()\` сейчас берёт текст только из \`state.description\` — поля **редактора СОП**. Для автономного старта анализа это неправильно; «Описание изучаемого процесса» должно вводиться непосредственно в «Анализе ФРВ» (или заполняться по инициативе пользователя из известного описания).
- По умолчанию «Анализ ФРВ» не использует заполненный лист «ФРВ» из СОП. Это не обязательно дефект: у разделов разное назначение. Нужен понятный UX и, возможно, явный необязательный импорт наблюдений из СОП без изменения уже сделанных замеров.
- \`frvStudyMakeSok()\` берёт только подтверждённые наблюдения с найденными AI-кандидатами; без AI-анализа создание проекта СОП фактически блокируется. Нужно позволить сформировать проект СОП из **подтверждённых человеком действий** и без обращения к облаку; ИИ лишь помогает оформить их.

## 2. Реальные дефекты (исправить перед принятием нового UX)

### P0 — повреждение/подмена существующего СОП

\`src/modules/frv/stage19-study.js\`: \`frvStudySendSop()\` выполняет \`state.steps=[]\` и создаёт новый список, **не показывая отдельного предпросмотра/подтверждения**. Это может уничтожить текущую редактируемую версию и связи с фото. **Функцию переноса сохраняем**, но делаем безопасной: по умолчанию «Создать новый проект СОП», показ старого/нового содержания, черновик/снимок для отката, подтверждение, не перезаписывать действующий СОП молча.

### P0 — нулевое время в кандидате и СОП

\`src/modules/frv/stage26-proposals.js\`: \`frvAiNormalizeAnalysis\` намеренно записывает \`standardTimeSec:null\` (ИИ не должен придумывать нормативные значения).
\`src/modules/frv/stage19-study.js\`: \`Number.isFinite(Number(a.standardTimeSec))\` ошибочно считает \`null\` числом \`0\`; так при формировании СОК-кандидата теряется реально измеренная длительность. Далее аналогичное преобразование может создать в СОП шаг с \`0\` сек. **Нельзя заменять замер «нулём по умолчанию».** Сохранять измеренное время отдельно, а стандартное/целевое оставлять \`null\` до обоснования и подтверждения инженером.

### P0/P1 — арифметика и отсутствие измерений

- Простая «ФРВ» может одновременно считать всю длительность как ВДЦ и прибавлять М1/М2 без проверки, что категории в сумме не превосходят время шага. Нужно взаимоисключение для однородных интервалов, явное разделение шага на интервалы при смешанном времени, валидация отрицательных значений и пояснения для существующих неоднозначных записей.
- В листе XLSX несколько итогов подписано «мин», но \`computeFrv\` даёт секунды; колонка «Длит-ть, сек» форматирует значение как \`h:mm:ss\`. Согласовать единицы/подписи, не сломав принятый шаблон.
- \`frvStudyDuration(null)\` возвращает \`0\`; такой «незамерен» может быть принят AI-анализом за реальный нулевой замер. Сохранять \`null\`, не выводить арифметический результат для неизмеренного действия без отдельного предупреждения; не отправлять в ИИ фиктивное время.
- После ручного изменения наблюдений старые итоги ИИ могут остаться показанными без явной маркировки «анализ устарел». Повторный анализ — отдельное сознательное действие.
- \`frvStudyBuild()\` добавляет AI-предложенные действия как новый «цикл» при существующих данных, хотя это ещё не наблюдавшийся повторный цикл. Предложения/черновые строки не должны смешиваться с фактами.

## 3. Целевой пользовательский сценарий — оставить отдельную вкладку «Анализ ФРВ»

**Основной поток без чрезмерных форм:**

1. **Начать исследование** — на странице «Анализ ФРВ»: название/место/исполнитель (опционально), что наблюдаем. Можно вручную добавить действия либо предложить черновой перечень ИИ из описания **в этом же разделе**; ИИ ничего не выдаёт за реальный замер.
2. **Провести наблюдения и замеры** — компактная таблица «Действие / Время (сек) / Тип времени / Комментарий / Перемещение»; повторные реальные циклы и материалы/инструменты/качество/безопасность/доказательства доступны через «Подробнее», а не 19 колонками сразу.
3. **Проанализировать** — расчёты без ИИ: продолжительность и доли ВДЦ/М1/М2, ожидание/перерывы отдельно, ранжирование потерь, сравнение реальных циклов и предупреждения о пропущенных замерах. По желанию «Предложить улучшения с ИИ» с объяснением и источниками; никакой автоматической замены RAW/фактического времени.
4. **Подготовить улучшенную последовательность для СОП** — выбор тех действий, которые войдут в будущий стандарт, порядок, ключевые моменты, причины, качество/безопасность и подтверждённые времена. **Не переносить в СОП потери и ожидания автоматически**; некоторые обязательные ожидания/проверки остаются по инженерному решению. Слова «СОК-кандидат» можно заменить в основном UI на «Проект шагов СОП», сохранив внутреннее представление.
5. **Создать СОП из анализа** — показывать предпросмотр нового проекта и объяснять, какие факты/замеры переносятся, какие ключевые моменты/риски надо доработать. **Создать новый проект по умолчанию**, не очищая прежний СОП. Любая замена/добавление к открытому СОП — только с явным выбором и подтверждением, с возможностью возврата. Далее стандартное редактирование, проверка/экспорт СОП и, при необходимости, отдельная генерация TWI из СОП.

**Сохранить две вкладки как различные входы:**
- «ФРВ» — существующий лист СОП, его приёмка, расчёты и XLSX; не превращать его в обязательное условие работы «Анализа ФРВ».
- «Анализ ФРВ» — собственный независимый исследовательский поток до подготовки СОП, с последующим **необязательным переносом в СОП**.

## 4. Что должно остаться в реализации

- Достоверность/неизменность RAW-действий, измеренных секунд, связанных доказательств и циклов; раздельное хранение черновых предложений ИИ.
- Прослеживаемость каждого будущего шага СОП до исходных наблюдений/циклов и решения инженера.
- Режим без ИИ: от замеров и ручной классификации до проекта СОП.
- Существующие Yandex Cloud-прокси/модели и выключенный \`SOP_ENABLE_MODEL_ROUTING\`; принятый XLSX Stage32.2, картинки/ISO, библиотека/черновики, генерация СОП и TWI.
- Дополнительные инженерные поля сохраняют доступность в расширенном представлении. Сложность интерфейса не должна определять обязательность таких полей.

## 5. План реализации после команды пользователя

**Один крупный пакет в отдельной ветке Stage33, без изменений принятой Stage32.2 до CI и пользовательской приёмки:**

1. Безопасность переноса СОП, исправление \`null→0\`, правильные единицы и проверки классификации времени, старения результатов анализа.
2. Независимый старт «Анализа ФРВ» без поля \`state.description\` в редакторе СОП, основная компактная форма наблюдений с расширенными деталями и реальными повторными циклами.
3. Анализ без ИИ, ИИ как необязательное дополнение; подтверждение улучшенной последовательности до передачи в проект СОП.
4. Предпросмотр создаваемого СОП, выбор «создать новый» по умолчанию, защита существующей работы, сохранение источника времени и RAW/доказательств.
5. Сквозная проверка «новое исследование ФРВ → измерения → анализ → новый проект СОП», включая режим без ИИ, сохранение/восстановление, сохранность оригинального СОП, XLSX Stage32.2/фото и регрессию TWI.

**Приёмка:** пользователь может открыть «Анализ ФРВ» в пустой программе, провести замеры, построить анализ, утвердить будущие шаги и создать новый СОП без предварительного заполнения редактора СОП. Открытый ранее документ не пропадает. Фактическое время не превращается в 0; ИИ не переписывает первичные данные.

## 6. Статус

**Уточнённый аудит и целевой сценарий записаны; код не изменён.** Stage32.2 остаётся принятой базой в \`main\`. Реализацию не начинать без команды пользователя.
