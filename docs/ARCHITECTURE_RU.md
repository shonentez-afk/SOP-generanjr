# Архитектура модульного Конструктора СОП

## Выполненный этап A1 — исходная модульность Stage19
- В исходниках присутствуют 39 частей src/modules/**/stage19-*.js; порядок фиксирует src/app/stage19-parts.json, сборщик tools/build_stage19.py соединяет их с локальными ExcelJS/ISO 7010 и HTML-оболочкой. Текст итогового HTML полностью совпадает со Stage18.
- Из крупного блока документов выделены DB, сеть, переносимые фото и синхронизация; ФРВ разделена на модели, ввод/вывод, ИИ-анализ и перенос в стандарт; общие blobToDataUrl и dataUrlToBlob теперь лежат в shared.
- Модули пока соединяются в один общий строгий JS script; не считать их полностью независимыми. A2–A4 должны обеспечить явные интерфейсы и убрать опасные побочные зависимости при сохранении старых данных.
- TWI/from-sop остаётся производным от СОП, без самостоятельного конструктора и обязательной ФРВ. Для пользователя — один автономный HTML на ПК.


## Приоритет модульной миграции — основной план от 19.11.2026
Основной документ: [DEVELOPMENT_PLAN_MODULAR_AI_TWI_20261119_RU.md](DEVELOPMENT_PLAN_MODULAR_AI_TWI_20261119_RU.md). Подробные причины прошлых сбоев: AI_CAPABILITIES_MODULARIZATION_AUDIT_20261119_RU.md.

**Разделение продолжаем.** Исходный монолит из src/legacy/inline-script-03.html и цепочка замен текста в build_stage12..18 не являются законченной модульностью. Следующая работа — крупный пакет A: один воспроизводимый сборщик с точным порядком подключений, затем независимые core/state и media/photo, excel/storage, ai/transport/protocol/tasks/presenter, app/bootstrap. При переносе сначала сохраняется поведение; новая логика вводится только после приёмки границ.

**Контракт TWI:** `twi/from-sop` получает снимок текущего СОП и автоматически формирует план четырёх этапов обучения. Ввод отдельного плана с нуля не предусмотрен; ручные правки после генерации необязательны. Изменение СОП требует проверки актуальности созданного TWI; повторная генерация защищает уже внесённые исправления. ФРВ для TWI не обязательна. Исходный документ — СОП; производный — TWI.

**Релизный инвариант:** разрабатываем несколько файлов, но пользователю передаём только один полностью автономный HTML под Chrome/Edge ПК с запуском через file://. Не требовать от пользователя сборщика, интернета для ISO-знаков, сервера или дополнительных JS-файлов.


## Результаты кодового аудита 19.11.2026 (предлагаемая эволюция, не реализована)
См. `docs/AI_CAPABILITIES_MODULARIZATION_AUDIT_20261119_RU.md` для доказательств ошибок и полного плана. Следующий архитектурный пакет выделяет независимые `ai/transport`, `ai/protocol`, `ai/tasks`, `ai/ui`, `shared/media` и `core/document-snapshot`. Главный инвариант: AI-результат — только валидированное предложение к конкретной неизменной редакции документа; применение только по подтверждению пользователя. Экспорт не должен изменять состояние редактора или буферы фотографий. Диалоги/решения должны храниться в версии документа при сохранении старого формата посредством миграции. Это проектное направление — существующие `src/modules/ai/` пока содержат лишь исправления Stage 17/18, а не автономную AI-платформу.


## Точка запуска
Исходники разделяются по файлам. При выпуске сборщик встраивает JS/CSS/локальные ассеты в один HTML, который пользователь открывает двойным щелчком. Разработка и конечный способ запуска — разные вещи. Не полагаться на `fetch(file://...)`, ES-import по `file://` или сервер.

| shared/ui | общие элементы, уведомления, диалоги |
| app/bootstrap | инициализация, привязка обработчиков, интеграция |

## Правила зависимостей
- Ядро не импортирует UI, Excel, ИИ или IndexedDB.
- ФРВ не вызывает прямую перерисовку вкладок; отдаёт результаты.
- Фоторедактор изменяет изображение через контракт чтения/записи медиа шага.
- Экспорт читает снимок документа, но не очищает черновики.
- Все модули должны поддерживать тесты без запуска полной страницы.
- Контракт сохранённых документов сохраняется при структурном переносе.

## Стратегия миграции
0. Зафиксировать неизменный baseline в `releases/`.
1. Вынести script/style в отдельные файлы и собрать в один HTML без изменения кода.
2. Установить границы состояния и побочные эффекты.
3. Переносить модули по одному, сравнивать с baseline, добавлять тесты.
4. Приёмка с реальными сценариями браузера и корректной работой XLSX.
5. Выпуск только после регрессии; `main` не использовать как экспериментальную ветку.

## Внимание
Встроенный `file://` файл не может надёжно реализовать конкурентную блокировку сетевой папки, инициализацию ES-модулей или доступ к соседним файлам без разрешения браузера. Не обещать таких функций без отдельной архитектуры.
