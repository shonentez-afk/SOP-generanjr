## 2. Вторая проверка связей: Acorn AST на исходниках Stage41

Мы не стали объявлять каждую связь CodeFlow реальным вызовом. Для всех **367 пар файлов и 687 записей символов** проведена отдельная синтаксическая проверка исходников через Acorn 8 + acorn-walk.

| Категория записей | Найдено |
| --- | ---: |
| Прямой вызов идентификатора в AST | **612** |
| Ссылка на идентификатор без прямого вызова | **47** |
| Не обнаружено соответствующего употребления | **28** |

По **367 парам файлов**: 324 имеют хотя бы один прямой вызов, 17 — только ссылки на функции, 26 — требуют уточнения. Для **58 оставшихся исторических дополнительных связей** распределение: 26 прямых, 9 только references, 23 не подтверждены этим AST-сканированием.

[Результаты AST с точными строками](stage41-ast-evidence.json) · [инструмент в репозитории](qa/stage41-ast-evidence.mjs) · [GitHub Actions #45154665601 — PASS](https://github.com/shonentez-afk/SOP-generanjr/actions/runs/45154665601).

**Уровни доказательности:**
- `direct_call`: синтаксически есть прямой `name(...)`, и найдено имя в целевом файле. Это ещё **не** доказательство правильного связывания имён при выполнении.
- `reference_only`: имя используется, например в колбэке/ссылке; путь исполнения требует дополнительной проверки.
- `not_found`: CodeFlow сопоставил функцию по своему анализу, но независимый AST не смог подтвердить обращение; возможны name-fallback, свойство объекта, переименование или динамика.
- Пример потенциального ложного сопоставления: метод `set.add()` нельзя автоматически считать вызовом пользовательской `add()` из другого модуля.

**Особый технический нюанс:** один старый источник `src/modules/documents/stage19-network-io.js` не парсится отдельно строгим Acorn (`Unexpected token (1:47)`); анализатор явно пометил и обработал его толерантным `acorn-loose`. Это **не доказательство неисправности выпущенного HTML**: Stage41 прошла свою сборку и браузерные тесты; вопрос самостоятельной валидности фрагмента можно проверить в основном чате отдельно. Никаких исправлений программы в этой ветке не делалось.

## 4. Фактический путь запросов ИИ Stage41

**Генерация СОП:** `generateSOP → aiAsk (Stage41 wrapper) → aiAsk transport → Yandex Cloud Function → YandexGPT`, затем существующая проверка JSON, Stage39.1-нормализация причин, guard актуальности и применение после предусмотренного решения пользователя.

**Полная проверка:** `reviewEntireSOP → aiAsk (Stage41 review prompt без NORM_BASE) → проверка цитат/evidence → Stage41 фильтр только точных подтверждённых AI-fix → Stage40 встроенное Сейчас / После применения`. Готовое исправление не применяется к изменённому документу.

**TWI:** `generateTwiPlan → Stage41 prompt → YandexGPT → aiReadTwiPlan → stage29TwiNormalize`. TWI строится исключительно из текущего СОП, без выдуманных Key Points, Reasons, новых норм/режимов.

**Индивидуальная ✨ «Причина»:** `stage391SafeReasonField → edit_reason → stage391ReasonAIInspect → guard → прямое применение` без дополнительного окна. Неверная WHY не записывается, допускается одна ограниченная повторная попытка. **Stage41 не меняет task `edit_reason`.**

**ФРВ:** новые Stage41-инструкции не добавлены к `frv_study_*`; наблюдения и замеры остаются фактическими данными, не изменяемыми ИИ.

Это **логические цепочки из кода и источников**, а не результаты перехвата реального сетевого трафика. Реальная YandexGPT не вызывалась в архитектурном исследовании.
