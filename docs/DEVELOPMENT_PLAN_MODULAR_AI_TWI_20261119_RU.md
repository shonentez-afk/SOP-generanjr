## 1. Неизменный пользовательский процесс

**СОП — основной документ. TWI — создаваемый из него производный план обучения.**

1. Пользователь создаёт или редактирует СОП (вручную либо с помощью ИИ).
2. При необходимости пользователь использует ФРВ для наблюдений и предложений по улучшению процесса; **ФРВ не обязательна** ни для создания СОП, ни для TWI.
3. Пользователь нажимает «Сформировать TWI»: ИИ **автоматически** создаёт все четыре этапа Job Instruction из имеющегося СОП, в том числе из черновика, не требуя самостоятельного заполнения TWI.
4. Пользователь просматривает результат и **только при необходимости** вручную корректирует сформированный TWI.
5. При значимом изменении исходного СОП (действия, Key Points, Reasons Why, критерии результата, условия безопасности) ранее созданный TWI помечается «Требует проверки» и предлагается обновление. При повторной генерации НЕ затирать ручные исправления без предпросмотра и подтверждения пользователя.
6. TWI не имеет отдельной от СОП логики составления с нуля, не превращается в самостоятельный мастер ввода и не требует предварительного утверждения СОП для первого формирования (действующая функция получает текущий state.steps).

**Целевая цепочка:** [ФРВ, необязательно] → СОП → автоматическая генерация TWI → [ручная корректировка, необязательно]. Не смешивать этот план с отдельной веткой TWI Audit RC1.

## 2. Продолжаем ли делить программу на модули?

**Да. Это следующий обязательный инженерный этап.** Сейчас в src/app/parts.json и src/legacy/inline-script-03.html основной код всё ещё объединён, а src/modules/ содержит преимущественно вынесенные функции/патчи отдельных версий. Сборщики Stage 12–18 продолжают заменять участки общего HTML строками. Это не завершённая модульная архитектура.

Разделение необходимо из-за доказанных перекрёстных зависимостей: Stage 15 при замене пиктограмм удалил общий blobToDataUrl и нарушил «Разметить»; экспорт Stage 16 использовал нормализацию черновика и потерял фото; Stage 17/18 обнаружили отсутствие общего строго проверяемого протокола ответа ИИ. При этом проблема ExcelJS с графическими якорями — самостоятельный дефект формата, который нельзя объяснить только монолитом.

**Цель:** структурно независимые исходники и одна воспроизводимая сборка **в один автономный HTML**, запускаемый двойным щелчком в Chrome/Edge на ПК через file://. Отдельный сервер, сборка на пользовательском компьютере, ES-import по file:// и соседняя папка с зависимостями не допускаются.

## 3. Целевая структура исходников и направление зависимостей

| Блок | Ответственность и контракт |
|---|---|
| core/state, core/snapshot | Схема СОП, версия/редакция, изолированные снимки, проверка прав на изменения, операции применений без потерь |
| shared/media | Единый Blob/dataURL/ArrayBuffer; получение и подтверждение изображения по идентификатору; не завязан на пиктограммы, Excel и UI |
| editor/steps | Шаги, ключевые моменты, Reasons Why, критерии; редактирование через core |
| photos/editor, photos/repository | Редактор разметки, оригиналы, фото шага, IndexedDB, версии; общий медиа-контракт |
| safety/icons | Локальная библиотека 60 ISO 7010; только свои ассеты; не владеет общим конвертером Blob |
| frv/measurements, frv/analysis | Фактические наблюдения/времена отдельно от ИИ-гипотез, детерминированные расчёты |
| ai/transport, ai/protocol | **Тот же** Yandex Cloud-прокси и настройки; разбор HTTP, JSON, ошибок, валидация по задаче; без доступа к живому state |
| ai/tasks, ai/presenter | Подготовка контекста и предложение изменений без применения; UI показывает ответы без keep/null и без служебного JSON |
| documents/storage, documents/network | Черновики, опубликованные версии, история замечаний, резервные копии, синхронизация и миграции |
| excel/import-export | Обмен XLSX по существующему формату; **только чтение** снимка и медиа при экспорте, без изменения state |
| twi/from-sop | Однонаправленная генерация TWI **из текущего СОП**, затем необязательные правки; связь с редакцией СОП, проверка устаревания; не отдельный редактор СОП |
| shared/ui, preview, app/bootstrap | UI, навигация, состояния ожидания, сборка/интеграция модулей и чистое отображение |

Важные правила: core ничего не знает о DOM/Excel/ИИ; AI не меняет state непосредственно; модуль export не нормализует живые шаги; TWI читает подготовленный снимок СОП и возвращает результат, который связывается с исходной редакцией; фото-конвертер не принадлежит safety/icons.

## 4. План крупных пакетов разработки

Работать **крупными проверяемыми пакетами**, а не десятками самостоятельных микроисправлений. Внутри каждого пакета допустимы последовательные контрольные точки и тесты; выпускать только завершённый пакет с одним HTML и документированной регрессией.

### Пакет A — завершить основную модульную архитектуру и защиту данных (самый высокий приоритет)

**A1. Сборка из исходных модулей.** От текущей Stage 18 зафиксировать эталон: HTML, файлы, список действий и воспроизводимые тесты. Заменить цепочку текстовых патчей Stage 12→18 на единый детерминированный сборщик с контролируемым порядком CSS/JS/ассетов. Перенести основной JS из src/legacy в исходные модули без изменения алгоритмов и пользовательского поведения. Не считать перенос завершённым, если основные функции остались только в монолите или требуют поиска/замены текста релиза для каждой сборки.

**A2. Обязательные общие контракты.** Вынести state/snapshot, медиа-функции, хранилище и чтение для XLSX. Экспорт должен получать неизменный снимок шага и реальные фото из памяти/IndexedDB через один контракт. Версии документов, архив и фото не смешивать.

**A3. Отдельный ИИ-слой.** Вынести transport/protocol/tasks/presenter, сохранив текущий прокси, список моделей, настройки, fallback как существующее поведение на этапе переноса и все тексты промптов без изменений. После рефакторинга отдельным проверяемым изменением унифицировать схему ответов и исправить ошибочные повторы/некорректные JSON/HTTP-ошибки. Для каждого результата фиксировать привязку к текущей редакции СОП.

**A4. Защита пользовательских правок.** При повторной генерации или изменении уже существующих СОП/ФРВ показывать сравнение и возможность принять/отменить. Не изменять фактические замеры и оригинальные фото. **Первая генерация TWI из СОП остаётся прямой и простой.** Только при повторном создании TWI с уже внесёнными правками показывать различия/подтверждение. Данные диалогов/замечаний сохранять по документу и версии, при изменении схем хранения делать миграции и обратную проверку старых черновиков.

**A5. Полная приёмка и готовый HTML.** Должен существовать только один актуальный файл выпуска в releases/; старые версии остаются архивом. Программа запускается через file:// на ПК. Никакой замены Yandex Cloud-прокси/провайдера и изменения модели «ради рефакторинга».

**Критерии завершения A:**
- Полный исходный код функций находится в модулях; есть карта зависимостей, один воспроизводимый сборщик и автоматическое сравнение сборки с эталоном/оговорённым diff.
- Структурное выделение модулей не меняет поведение на контрольных сценариях; локальные 60/60 знаков работают без сети.
- Фото загружается → размечается → сохраняется → восстанавливается из IndexedDB → экспортируется в XLSX вместе с логотипом и пиктограммами; проверка 3/3 изображений и OOXML.
- ИИ: корректный JSON, незавершённый JSON, обычный текст, 401/403/429/5xx, пустой ответ, таймаут, повтор/отмена, сохранение результатов и человеческое отображение без служебных полей.
- Генерация СОП/ФРВ не удаляет подтверждённые данные без явного согласия; опубликованные версии защищены.
- Первый TWI успешно создан **из СОП**, без ручного ввода и требования ФРВ; поправленный TWI сохраняется, а повторная генерация не уничтожает корректировки без подтверждения.
- Тесты восстановления старых черновиков, версий, резервных копий и истории; Chrome/Edge file://, реальная IndexedDB, Excel и сетевая папка проверяются отдельно при доступности Windows/реальной среды.
- Весь предыдущий CI Stage 12–18 остаётся зелёным; отсутствуют новые зависимости пользователя.

### Пакет B — улучшить интеллект работы с СОП и ИИ-наставником (после A)

1. Умная проверка Important Step → Key Point (0–3, **ноль допустим**) → Reason Why → критерий результата; не вынуждать пользователя создавать фиктивные ключевые моменты.
2. Условное предложение фото: учитывать imageData, imageBuffer, hasPhoto, IndexedDB; отсутствие фото не всегда ошибка. Давать один лучший кадр по фактическому действию, не утверждая, что ИИ видел изображение.
3. Проверка безопасности и качества с указанием подтверждённых исходных данных: явно известное, предположенное, требующее уточнения. Не придумывать ГОСТ, допуски, СИЗ, значения и не утверждать СОП автоматически.
4. Наставник: осмысленные замечания, аргументированное обсуждение, статус «оставить/снять/проверить локально», история по документу/версии, сохранение после перезапуска.
5. При доработке шага показывать короткое объяснение и сравнение «было → предложено», затем «Принять / Отклонить». Повторная проверка только изменённых шагов без потери существующих замечаний.
6. Не превращать TWI в параллельный мастер. В пакете B допускается улучшать качество текстов, которые *автоматически* создаются из СОП, но не расширять ручной ввод TWI.

**Приёмка B:** эталонные синтетические СОП, отсутствие ложных Key Points/фото-замечаний, отсутствие придуманных нормативов, отклонённое предложение не меняет документ, история проверяема.

### Пакет C — согласованная цепочка ФРВ (при наличии) → СОП → TWI

1. ФРВ — только при потребности пользователя: исходные наблюдения и замеры неизменяемы, ИИ предлагает интерпретацию потерь и вариантов улучшения, подтверждённое время считается детерминированно.
2. Из выбранных и подтверждённых строк ФРВ можно подготовить/обновить СОП с происхождением observationId; **можно создать СОП и без ФРВ**.
3. После составления СОП пользователь одной кнопкой автоматически генерирует четыре этапа TWI JI. Входные данные — шаги, Key Points, Reasons Why, критерии результата и доступные сведения безопасности из текущего СОП; **не отдельная анкета TWI**.
4. Если СОП изменился после создания TWI, показывать только сообщение «План TWI может устареть» и вариант «Обновить из СОП»; при повторном запуске показать изменения и сохранить ручные правки по выбору пользователя.
5. Проверять, что TWI относится к правильной версии СОП, не ссылается на удалённые шаги, не добавляет неподтверждённые действия или опасные требования. Материалы для обучения и вопросы также генерировать из СОП, без ручного составления с нуля.
6. Локальная библиотека утверждённых стандартов как справочник подтверждённых источников — отдельное необязательное улучшение; не передавать производственные данные внешнему ИИ без ясного разрешения.

**Приёмка C:** две траектории (СОП→TWI и ФРВ→СОП→TWI) работают; ФРВ не требуется для TWI; изменения СОП корректно помечают зависимый TWI; ручные поправки защищены; импорт/экспорт и версии сохранены.

## 5. Что НЕ делать

- Не создавать отдельный самостоятельный TWI-конструктор, обязательные поля ручного TWI или отдельный рабочий процесс от черновика до утверждения TWI.
- Не требовать выполнения ФРВ, прежде чем сформировать TWI.
- Не заменять существующий Yandex Cloud-прокси, список моделей, маршрутизацию, промпты и AI-конфигурацию при чистой модульной миграции.
- Не ломать IndexedDB/localStorage или сетевую библиотеку без версионированных миграций.
- Не переносить сборку в обязанности пользователя: итогом остаётся один автономный HTML.
- Не исправлять телефонную горизонтальную прокрутку — мобильная версия исключена из объёма.
- Не смешивать неиспытанные идеи с реализованными функциями и не выдавать CI со стабами за проверку реального корпоративного прокси.
